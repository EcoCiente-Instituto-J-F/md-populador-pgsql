Por que manter o backup lógico

O sistema aceita Neon e Aiven (a conexão é uma DSN PostgreSQL comum); o ambiente de referência é o Neon, plano free, com limite de 1 GB. Os recursos de recuperação do provedor dependem do plano; o console diz o que o free cobre. Mantemos o backup lógico mesmo assim, por quatro motivos.

  1. Independe da conta. Os backups do provedor em geral somem junto com o serviço; o dump fica com a equipe.
  2. É portátil. Serve entre provedores e versões: Neon, Aiven ou PostgreSQL local.
  3. Restaura uma tabela só, sem voltar o serviço inteiro no tempo.
  4. Dá para testar todo mês num PostgreSQL local, sem tocar na produção.

Como fazer backup

Um comando, do backup.sh ou do backup.ps1.

  1. Defina ECOCIENTE_DSN no ambiente ou no .env (o script lê só essa linha; veja .env.example).
  2. Tenha o pg_dump 16 ou mais novo no PATH, ou aponte PG_BIN para a pasta dele. A versão deve ser igual ou maior que a do servidor.
  3. Rode o script (comandos abaixo), da raiz do repositório.
  4. Confira a linha ok: e as linhas mantido: e apagado: da retenção.
  5. Copie o .dump para fora do servidor do banco.
Linux, macOS e Git Bash
scripts/backup/backup.sh
Windows (PowerShell)
.\scripts\backup\backup.ps1

Se o pg_dump falhar, o script imprime ERRO: pg_dump falhou (código N). Nenhum backup novo foi gravado. e sai com código 1. Não fica arquivo parcial.

Como restaurar

Banco inteiro, uma tabela ou só a conferência por contagem.

Banco inteiro, num banco novo
  1. Crie um banco novo e vazio (no serviço novo ou num PostgreSQL local).
  2. Rode restore.sh com o dump e a DSN do banco novo. Ele executa pg_restore --clean --if-exists --no-owner --no-privileges --exit-on-error.
  3. O script recusa um destino igual a ECOCIENTE_DSN. Para restaurar por cima de propósito, exporte ECOCIENTE_ALLOW_RESET=1.
  4. Confira com --comparar (abaixo).
Linux, macOS e Git Bash
scripts/backup/restore.sh backups/ecociente_AAAAMMDD_HHMMSS.dump \
  "postgres://usuario:senha@host:5432/ecociente_restaurado?sslmode=require"
Windows (PowerShell)
.\scripts\backup\restore.ps1 backups\ecociente_AAAAMMDD_HHMMSS.dump `
  "postgres://usuario:senha@host:5432/ecociente_restaurado?sslmode=require"
Uma tabela isolada

Restaurar uma tabela só (pg_restore --data-only -t). Sem --truncar, linhas que já existem colidem com a chave primária. O --truncar não usa CASCADE: se outras tabelas referenciam a restaurada por FK, liste todas juntas com -t. O caminho mais seguro é restaurar o dump inteiro num banco novo e copiar as linhas de lá.

scripts/backup/restore.sh -t tb_cursos [--truncar] backups/ecociente_AAAAMMDD_HHMMSS.dump "<dsn_destino>"
.\scripts\backup\restore.ps1 backups\ecociente_AAAAMMDD_HHMMSS.dump "<dsn_destino>" -Tabela tb_cursos [-Truncar]

Teste de restauração mensal

Todo mês, na primeira semana, pelo responsável pelo banco.

Quem executa: o responsável pelo banco (perfil DBA / Admin do catálogo de dados), com uma segunda pessoa conferindo o resultado.

  1. O último dump existe e tem menos de 24 h.
  2. O tamanho é coerente com o do mês anterior.
  3. Suba um PostgreSQL 16 local: docker run --rm -d -p 15432:5432 -e POSTGRES_PASSWORD=teste postgres:16.
  4. Crie um banco novo e vazio nele.
  5. Faça um backup novo e rode restore.sh --comparar logo em seguida, para a origem não ter mudado.
  6. Confira que as contagens são iguais (sem linha DIVERGE).
  7. Aplique o .schema.sql num banco vazio e confira que não dá erro.
  8. Anote os tempos de backup e de restauração e compare com o mês anterior.
  9. Apague o banco de teste e confira que a retenção mantém 7 + 4 arquivos.

Como medimos

Um teste real, num PostgreSQL 16 local.

Como o teste foi feito
  1. Contêiner postgres:16 local.
  2. Schema e depois o Data Mart (o teste foi feito com o índice corrigido numa cópia; o arquivo do repositório já tem a correção).
  3. Populador com --escala leve --force: 17,4 s.
  4. CALL sp_carga_datamart();
  5. backup.sh dentro do contêiner: 0,5 s, dump de 1,5 MB.
  6. restore.sh --comparar num banco novo (ecociente_restaurado): 2,0 s, 17 de 17 contagens iguais.
Limitações
  • Escala leve, uma máquina local, uma execução, sem rede.
  • O banco tem 28,1 MB; o de produção será maior e os tempos crescem com ele.
  • O tempo de restauração é só a etapa do pg_restore; o script inteiro, com as contagens, leva mais.
  • Os scripts .ps1 foram validados de ponta a ponta no PowerShell 7 (em contêiner); no Windows PowerShell 5.1 só até a checagem do pg_dump.
